# CampusSphere local demo runbook

Ordinary local development uses the dedicated SQLite fixture at `backend\campussphere_demo.sqlite3`. With the default `CAMPUSSPHERE_ENV=development`, the backend ignores `.env`, selects this exact fixture, and refuses to start unless its demo marker is present. To use the existing shared/production configuration intentionally, set `CAMPUSSPHERE_ENV=production`; the backend then reads `DATABASE_URL` from the process environment or `backend/.env`. Never use production mode for a local demo.

## Requirements

- Windows PowerShell, Node.js/npm, the installed frontend `node_modules`, and `backend\venv`.
- The local fixture generated by the guarded `backend\generate_demo_data.py` script.
- No production/shared database configuration is required.

## Standard local startup

From the repository root, run the backend with the normal command:

```powershell
cd backend
.\venv\Scripts\Activate.ps1
python -m uvicorn main:app --reload
```

The local development backend uses port `8000`, only the marked local SQLite fixture, and a process-local signing key. Keep this terminal open. Restarting it invalidates existing sessions, so log in again. If port `8000` is already occupied, do not stop an unknown service; identify it before choosing another port.

In another terminal from the repository root, run the frontend:

```powershell
npm run dev
```

Open `http://localhost:5173`. Vite binds to localhost on that strict port; the API client defaults to backend port `8000`. The local Vite origin is explicitly allowed by CORS. Log in with one of the local-only accounts documented in [backend/LOCAL_DEMO_DATA.md](backend/LOCAL_DEMO_DATA.md). These credentials are for the isolated demo fixture only.

An explicit `VITE_API_BASE_URL` can override the local default when intentionally using another backend. Do not point a local demo session at Neon or a shared database.

## Demonstration sequence

1. As admin, show the building/room directory and demo-only room/floor labels. Demo rooms are not verified inventory and cannot be changed through room management.
2. On Dashboard and Analytics, review operational counts first, then enable the explicit demo preview to show fictional demo counts and historical trends.
3. On Occupancy and Energy, show the default operational filter, then enable the clearly labelled simulated preview. Readings are historical fictional values, not live telemetry.
4. As student, browse buildings and rooms, open the notice and emergency feeds, and use the dashboard **Report an Issue** shortcut to inspect manual issue reporting. The form requires a building, room, title, description, and priority; category is not stored by the current API. Room booking checks conflicts on the backend, but no live availability feed is connected.
5. Only when an explicitly approved demonstration write is intended, use a DEMO room to submit a fictional local booking or maintenance request. The UI labels the data, and the API accepts these demo-room workflows only while the isolated SQLite fixture marker is active. Return as admin to review requests and supported status controls. Do not publish demo notices.
6. Show the CAD-based Digital Twin separately from verified operational records. Predictions remain unavailable unless the UI states otherwise.

## Safe local checks

From the repository root:

```powershell
& .\backend\venv\Scripts\python.exe .\backend\generate_demo_data.py --preview
$env:PYTHON_DOTENV_DISABLED = '1'
$env:CAMPUSSPHERE_ENV = 'test'
$env:DATABASE_URL = 'sqlite:///:memory:'
Set-Location .\backend
& .\venv\Scripts\python.exe -m unittest test_authorization test_demo_db_setup test_local_demo test_maintenance test_password_reset test_provision_user test_resource_integrity test_room_creation test_seed_campussphere_dashboard_demo test_seed_campussphere_demo test_student_workflows test_database
Set-Location ..
node --test
npm.cmd run lint
npm.cmd run build
```

The backend tests use fake sessions, in-memory databases, or temporary SQLite files. The database configuration tests do not connect to `.env`; the production-resolution test checks the dialect only. Do not run `test_db.py`, which attempts a configured database connection.

## Reset the local fixture

To deliberately recreate the demo fixture, stop the demo backend and remove only the exact disposable SQLite file:

```powershell
Remove-Item -LiteralPath .\backend\campussphere_demo.sqlite3
& .\backend\venv\Scripts\python.exe .\backend\generate_demo_data.py
```

On a new file, the generator prompts for hidden local-only admin and student passwords and stores only their existing password hashes. This deletes demo records in that one local file and does not affect another database. Never use a wildcard, directory path, `.env` value, or shared/production database for reset.

## Boundaries

- Local demo users support only the existing `admin` and `student` roles. There is no facilities/staff role in the current authorization model.
- Notices are fictional drafts. Student-facing notice endpoints exclude demo titles even if a legacy demo notice was previously published.
- Emergency alerts in the fixture are explicitly fictional and locally labelled; demo alerts are suppressed from student-facing endpoints outside the active local demo fixture.
- Events, resource/facility catalog, and forecasts do not have separate persisted models in this repository. Do not represent static CAD annotations or UI-only content as verified records.
- `backend\generate_demo_data.py` is distinct from the existing Neon-oriented seed scripts. Do not run those seed scripts for this local demo.
